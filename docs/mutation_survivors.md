# Mutation survivors

Every mutant this repository's tests failed to kill, and what each one means.

`docs/DEFENSIBILITY.md` listed "no mutation testing" as the only **HIGH**-severity open
hole, and gave the reason: every other gate here assumes somebody chose the right thing to
assert. Mutation testing is the only mechanical check on that assumption. It edits the
source one change at a time and asks whether any test notices. A test that passes against
both the correct and the broken version is worth nothing, and nineteen tests in this repo
were exactly that (H-004) — found by hand, in adjudication, not by any gate.

So the value of this file is not the score. It is the list. **A high score with no
survivors listed would be a suspicious result, not a good one** — it would mean nobody
looked.

## How to run it

```
nox -s mutation                  # the full scoped run, then the ratchets
nox -s mutation -- bm25          # one group (no ratchet: partial scope)
nox -s verify-mutation-scope     # prove no group's test command is missing a killer
```

Scope, per-group test commands and the ratchet floors are in `setup.cfg`. The tool is
`mutmut==2.4.5`, pinned: mutmut 3.x prints "please use the WSL" and exits before it
imports anything on Windows, and the module below that guard needs `resource`, which does
not exist there at all. The run happens in a scratch copy of the tree outside the
checkout, because mutmut mutates files **in place** and doing that in a shared working
tree hands anybody else running pytest a deliberately broken source file a few thousand
times in a row.

## What was run, and what was not

| | |
|---|---|
| mutated | `domain/services/` (5 modules), `application/use_cases/match_schema.py`, `infrastructure/adapters/sparse_retrievers/bm25.py` |
| mutants | 1607, all decided; nothing skipped, nothing sampled |
| **excluded** | every other file in `src/`. This is a scoped run, not a repo-wide one: the whole package is roughly ten times this size and would not finish. |
| test command | per group, in `setup.cfg` — the smallest subset that reaches every line of that group's targets |

The per-group commands are not a guess. `nox -s verify-mutation-scope` compares, per target
file, the set of lines a group's command executes against the set the **whole** suite
executes, and fails if the whole suite reaches a line the group does not. It found a real
gap on its first run: five lines of `match_schema.py` (251, 794, 1129, 1207, 1242) that
only `tests/properties/test_conservation.py` reaches. Without that test in the command,
mutants on those lines would have "survived" for no reason except the wrong command. It is
green now.

`ok_suspicious` counts as **killed**. mutmut flags a mutant that way when the tests killed
it but took more than twice the baseline; on a box running other work that threshold is
crossed for reasons having nothing to do with the mutant (H-007 measured a 30% throughput
band under load), and scoring it as survived would make a correctness ratchet move with the
machine's load. `bad_timeout` counts as **not** killed: the command never finished, so no
assertion is known to have fired.

Wall clock is not reported as a measurement. This ran on a box with about twenty other
agents working, and it took several hours including one deadlock and one file re-run. On
an idle machine expect the domain group at well under a second per mutant and the
match-schema group at two to three; anything more precise needs measuring idle.

## Three kinds of survivor

432 **TABLE** — the mutant edits one row of a lookup literal: one abbreviation, one
type-pair score, one domain pattern. Behaviour genuinely changes, so it is a real gap, but
a different KIND of gap from an unasserted branch. These dominate the raw count
(`alias_generation.py` is 51 lines of contraction table out of 240) and would otherwise
make the headline score a function of how long a dictionary happens to be. That is why the
logic-only column exists.

92 **UNCOVERED** — no test in the group's command executes the line at all. A
coverage gap, not an assertion gap; `make test-cov` is the gate for those.

287 **LOGIC** — an executed line of real code whose mutation nothing noticed. This
is the category mutation testing exists to find, and it is where every finding below that
matters lives.

## How to read a triage

Each row says HOLE, EQUIVALENT, NEAR-EQUIVALENT, DEAD CODE or UNCOVERED, and then why.
Where a triage cites a specific test by name, that test was read.

Every one of the 287 LOGIC rows carries a triage written for the source line it
sits on — not a rule, not a pattern. The TABLE rows and most of the UNCOVERED rows share
one sentence each, stated once at the head of their section, because the finding genuinely
is the same one repeated: "no test exercises this row of this table", "no test executes
this line". Saying that 432 times individually would be a longer file, not a more honest
one.

Three survivors and one kill were reproduced **by hand** in a separate checkout, applying
the edit to the source and running the group's own command, to prove the harness measures
what it claims:

| mutant | mutmut says | reproduced by hand |
|---|---|---|
| `context_enricher.py:122:0` `ContextEnricher.__init__ include_hierarchy=True → False` | killed | command exits 1 |
| `context_enricher.py:88:0` `EnrichmentConfig.include_hierarchy=True → False` | survived | command exits 0 |
| `alias_generation.py:191:0` `share_count > max_share → >=` | survived | command exits 0 |

That check also caught a defect in the reproduction itself, worth recording because it
would corrupt any mutation run: CPython invalidates a `.pyc` on the source's mtime **in
whole seconds** plus its byte length, so a mutation that preserves length (`==` → `!=`,
`True` → `None`) applied and reverted inside one second leaves the next run importing the
previous mutant's bytecode. The surviving mutant above read as killed until bytecode
writing was disabled. mutmut sets `PYTHONDONTWRITEBYTECODE=1` for its own subprocesses;
`noxfile.py` now sets it for every process it starts.

## What this found that no other gate here could

**Every measured constant in the scope is unpinned except two.** The repository records,
in comment blocks, the experiments behind `dictionary_alias_count = 0` (−18.8 P@1 at 30k
entries with it on), `include_type = False` (−2.1 P@1 with it on), `include_hierarchy =
True` (+20 P@1), `max_share = 3` (aliasing shared names cost 11.3 P@1), `max_aliases = 6`
(8 was worse), `expand_query_abbreviations = False` (0.691 → 0.671 with it on), and all
five scoring weights. Mutating any of them passes the entire suite.
`auto_approve_threshold = 0.87` and `fusion_alpha = 0.90` are the exceptions —
`tests/unit/application/test_matching_config.py` pins those two by value and stops. The
calibration is guarded on one side only.

**The weighted confidence can have four of its five terms sign-flipped.**
`match_schema.py:310` computes `w_sem*sem + w_lex*lex + w_edit*edit + w_type*type +
w_domain*domain`. Changing any of the last four `+` to `-` survives. Nothing checks that
confidence against a hand-computed value; the tests check relative ordering, and with the
other four weights between 0.05 and 0.15 the 0.70 semantic term keeps the order intact.
This is the H-004 shape in a new place: an oracle that can only see divergence, blind to an
error that moves everything together.

**One vacuous assertion.** `tests/unit/domain/test_context_enricher.py::
TestContextEnricherNestedFields::test_array_field_indicates_array_context` asserts
`"array" in result or "list" in result or "tags" in result` — and `"tags"` is the field
name, always present. The assertion is true for any output at all. Two mutants survive on
it: the `"array"` literal and the `and` that decides whether to append it.

**Boundaries are systematically untested.** `is_alias_worthy` is asserted at share counts
1 and 30 but never at 3 or 4, where its threshold is. `was_expanded` is asserted at 0
expansions and at 2, never at 1. `is_compatible` is never asserted at exactly 0.5, which
is the score the scorer returns for every unknown type combination. The cousin rule
`d1_dist <= 2 and d2_dist <= 2` survives widening either side.

**Dead code the name-count could not see.** `TypeCompatibilityScorer.strict_mode` is
stored and never read anywhere in the module, so no mutation of it can change behaviour —
the docstring promises "only exact matches score 1.0" and nothing implements it. Three
`reset_default()` classmethods have no caller; removing their decorators changes nothing.
`docs/DEFENSIBILITY.md` tracks "85 unreferenced public methods" as a name count that
"cannot prove reachability"; these are four of them, proven unreachable by experiment.

## Known limits of this run

- **Scope.** Six files. Everything else in `src/` is unmeasured, and an unmeasured file is
  not a passing file.
- **mutmut deadlocks on Windows.** Once in this run, 245 mutants from the end, both of its
  processes at 0% CPU with an orphaned pytest still holding the pipe. The cause: a mutant
  turned `while f"{key}#{n}" in taken` into `not in`, pytest looped forever, and mutmut's
  own timer killed only the `cmd.exe` shell, not the pytest grandchild. Two mitigations
  landed: the runner passes `--timeout=60` so pytest ends itself, and `nox -s mutation`
  watches for "no mutant decided in 10 minutes" and restarts from the cache, reporting each
  restart. A mutant that hangs the suite is scored as killed, which is honest — the suite
  did detect it.
- **The intervention that followed cost a re-run.** Killing the wedged run left a mutated
  file and a cache whose recorded source hash no longer matched, and 15 of 464
  `match_schema.py` mutants became unreachable. That file's rows were deleted and the whole
  file re-run from scratch rather than reporting a score over a denominator with a hole in
  it.
- **Equivalent mutants are not free.** Annotation-only edits are unkillable because
  `from __future__ import annotations` means annotations are never evaluated. They are
  marked EQUIVALENT and still counted in the denominator, which understates the score
  slightly. Removing them from the denominator by hand would be a judgement call inside a
  number that is supposed to be mechanical, so they stay.
